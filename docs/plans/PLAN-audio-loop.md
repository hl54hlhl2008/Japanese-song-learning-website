# 单句循环的手机端可靠性计划

**决定**：选 B，用 Web Audio 调度前台单句循环，保留 HTMLAudio 供普通逐句播放、连续跟唱和兼容回退。发布以真机录到的句首、句尾和回环间隔为准。锁屏、切后台和音频焦点中断纳入恢复行为验收，持续后台循环另立需求。

本文按节标题下的条目顺序引用 [luna 的调研](../research/audio-loop-platforms.md)，并保留其证据边界。下列性能阈值是本项目拟定的验收目标。

## 1. 现状评估

当前 `<audio preload="metadata">` 负责加载和播放。逐句入口在元数据未到时暂存请求，句首取 LRC 时间减 0.5 秒并限制在零以上，句尾取下一句时间戳，末句优先取音频时长，时长未知时取句首后 8 秒。代码先将区间拉到至少 0.12 秒，再对开启循环且区间仍短于 0.3 秒的情况采用最长 5 秒的回退区间。开始时写入 `currentTime` 并调用 `play()`。播放中由 `timeupdate` 在 `clipEnd - 0.04` 处判断边界，循环时写回句首，关闭循环时暂停。`ended` 提供文件末尾的回跳路径。`1430` 处是连续跟唱的起始 seek，该模式用 `timeupdate` 更新高亮。当前元素没有接入 `seeking` 或 `seeked`，逐句起播和回跳的 seek 异常也没有显式重试。 [App.jsx 的播放入口和事件绑定](../../src/App.jsx#L1361-L1502) · [音频元素](../../src/App.jsx#L1706)

## 3. 决定与理由

选 **B** 优先解决前台节拍。把句首和句尾交给音频时钟调度，避开 A 每轮都要等 JS 检测并重新 seek 的路径，同时让 Android 壳和 Web 共用循环逻辑。首选用同一节点在有效区间内循环，先证实 `loopStart` / `loopEnd` 的行为。启停以音频时钟定位，换句、换歌或重新开始时使用新节点；停止、暂停和倍速切换均须能作废旧播放请求。 [调研 §1 第 1–5 条、§2 第 1–2 条](../research/audio-loop-platforms.md#L5-L16) · [调研 §7 第 1–4 条](../research/audio-loop-platforms.md#L54-L59)

沿用 0.5 秒句首提前量、现有短句回退和末句取时长策略，以最终有效区间为验收基准。关闭循环时播完当前一轮即停；用户再次点句时从句首开始。收到可识别的后台或中断信号时结束本轮播放状态，回前台保持停止，等用户点按重播。生命周期信号和 iOS 静音行为均须真机核对。对解码失败或超出已验证资源预算的输入保留带提示的 HTMLAudio 兼容循环，并允许普通播放继续可用。当前可以播放的常用格式和四档慢放均为回归验收范围。 [App.jsx 的区间计算](../../src/App.jsx#L1361-L1410) · [调研 §3 第 1–3、6 条](../research/audio-loop-platforms.md#L22-L29) · [调研 §4 第 1–3 条](../research/audio-loop-platforms.md#L31-L35) · [调研 §7 第 4–7 条](../research/audio-loop-platforms.md#L59-L62)

## 4. Pi 执行 spec 草稿

### 任务 1 · 搭建判定基线

- **目标**　测当前实现的前台回环和中断表现，确认 B 的实现前提与资源预算。用自行生成、边界两侧带可识别标记的音频和配套 LRC，按当前句首提前量设计夹具。覆盖中间句、短句回退、文件末句和 10 分钟长音频。对现有导入入口分别试 MP3、M4A、WAV、OGG 及 WebM，记录容器、编码与原本能否播放。
- **允许改的文件**　仓库内无手工改动。夹具、录音、诊断数据和验收记录存 `/tmp/uta-audio-loop/` 或测试设备本地。使用现有 `npm run lyrics:sync`、`npm run web -- --host 0.0.0.0` 和 `npm run android:run` 启动，构建生成物留在本地。
- **验收标准**　有 iOS Safari、Android Chrome、Capacitor 壳三份基线，记录机型、OS、浏览器版本、壳的 WebView 版本、输出路径及结果。Android 壳覆盖常用设备，并记录是否测到 README 声明的最低 Android 版本。每种前台速度在空闲和可重复的 UI 负载下，各录至少 20 次回环。用边界标记分开统计实际句首和句尾的绝对偏差、回环停顿或重叠，统一用实际输出时间；同时将事件间隔及 `seeking` 到 `seeked` 的耗时作诊断记录。补查 Web Audio 循环点、停止时刻、手势激活、生命周期信号、输入读取、倍速音高，测长音频解码时间及峰值内存并记录拟采用的资源预算。按第 3 节的条件复核选型。

### 任务 2 · 实现可单测的 B 循环调度

- **目标**　对已解码的 buffer 按有效区间和倍速调度播放、停止和换速。每次重启创建新节点，保证同一时刻仅当前播放请求有效。能在关闭循环时于当前一轮句尾停止，并对无效区间返回可处理的失败。具体循环 API 以任务 1 补查结果为准。
- **允许改的文件**　`src/lib/audioLoop.js`、`tests/audioLoop.test.mjs`。
- **验收标准**　`node --test tests/audioLoop.test.mjs` 通过。用模拟音频时钟验证指定区间、起止调度、四档速度、中途换速后按当前轮定位、关闭循环到句末停止、立即暂停、重新播放使用新节点，以及失效节点的回调无法重启旧句。实际出声精度留给任务 4 录音判定。

### 任务 3 · 接入应用入口与兼容回退

- **目标**　接入网页和 Android 学习页的现有单句循环入口，包括引导练习。按当前音频源获取完整数据，用已验证的资源预算限制解码。只保留当前音源的一份解码缓存，音源变化时释放旧缓存并使待处理请求失效。HTMLAudio 与 Web Audio 互斥播放，异步失败提供可观察的兼容提示并在需要时等待再次点按。如果真机确认 iOS 静音行为分化，提供用户可主动选择的兼容入口，静音开关能否由网页识别需补查。接入任务 1 已确认可观察的中断信号。
- **允许改的文件**　`src/App.jsx`。
- **验收标准**　`npm run build` 和 `npm run android:build` 通过。手动覆盖首次点击、快速换句/换歌、同歌替换音频、暂停后重播、播放中开关循环、四档慢放、解码失败和前后台往返。无双重出声、过期解码后自动播放、回前台擅自重播或播放图标卡在旧句。关闭循环时当前轮播完即停。普通逐句播放、原有练习入口和连续跟唱的播放、高亮与 1× 行为可复验；网页和 Android 壳上的音频来源各覆盖一次项目音频与本地导入。

### 任务 4 · 按录音与真机矩阵决定是否发布

- **目标**　使用任务 1 的夹具、机型和负载复测，分别报告精确循环与兼容循环的结果。记录静音开关、锁屏、切应用和焦点中断后的声音与界面恢复。
- **允许改的文件**　仓库内无手工改动，录音及结果表存 `/tmp/uta-audio-loop/` 或测试设备本地。
- **验收标准**　拟定硬门槛为三类客户端在前台空闲和规定 UI 负载下，对精确循环的每档速度各测至少 20 轮。以有效区间在该速度下的参考输出为准，句首、句尾偏差和回环额外停顿或重叠分别满足 P95 ≤ 30 ms、单次 ≤ 60 ms。每轮都要出声，且偏差容限之外的下一句标记不得混入。四档速度还要与旧播放器对照，避免引入影响辨音的音高变化。已有常用输入在其原可播放平台上应继续可用，任何降级须明示。长曲和连续换歌不得发生崩溃或旧音源继续出声，峰值内存和首次起播须符合任务 1 记录的预算。未达标或未覆盖的场景在结果里明列，按第 3 节重评发布范围。未实测的系统或浏览器版本保留为未覆盖。
